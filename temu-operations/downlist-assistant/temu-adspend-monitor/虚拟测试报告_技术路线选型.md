# 虚拟测试报告：Temu 商品推广花费监控技术路线

测试日期：2026-10-22  
测试窗口：比特浏览器 `9e6f73cc742b4abc9015f31f8e75fbd7`，序号 `7512`，名称 `Y2-18`  
测试性质：真实只读探测 + 确定性蒙特卡洛模拟  
结论：采用页面主世界 `fetch`，不刷新整页，不以 DOM 文本作为主要数据源

## 1. 测试目标

回答三个问题：

1. 能否通过 `fetch` 直接读取今日花费，而不是刷新整个网页？
2. 哪种技术路线在数据完整性、成功率、延迟和自动暂停可靠性之间最优？
3. 哪些结论是实测，哪些是模拟假设？

## 5. 结果解释

### 5.1 页面主世界 fetch 最优

原因：

- 与页面同源，登录态和请求环境一致。
- 能取得完整的分页数据，不依赖当前可见行。
- 不触发多余报表、退款和建议接口。
- 不反复重绘数据区。
- 能直接用于自动暂停前后的状态核验。

### 5.2 DOM 很快但不完整

DOM 文本在本机测试中能快速看到当前页，但：

- 当前页面只渲染 10 行，而接口有 19 行。
- 多页时无法保证所有 SPU 都被覆盖。
- 文本格式化、自定义列和虚拟滚动会增加误判。

因此 DOM 不用于花费判断。

### 5.3 页面刷新路线可用但不适合长期运行

页面刷新确实能在不刷新整页的情况下更新数据，但每次会调用多个无关接口，并重绘数据区。作为人工备用入口可以保留，不适合秒级自动监控。

### 5.4 后台直连风险较高

扩展后台不在商品推广页的完整运行上下文中，Cookie、同源和风控行为更难保证。它适合调度，不适合作为 Temu 接口的唯一直连方。

## 6. 最终技术选型

采用：

```text
扩展 UI / 调度
    → Content Script
    → MAIN world page bridge
    → 同源 fetch
```

保留：

- 页面健康检查。
- 失败时的只读 DOM 数量校验。
- 人工“使用页面刷新”备用按钮。

不保留：

- DOM 文本作为金额来源。
- 每轮刷新页面数据区。
- 后台 Service Worker 直接请求 Temu 明细。

## 7. 自动暂停虚拟场景

建议在正式开发测试中覆盖以下场景：

## 8. 大店铺分页回归

2026-10-22 在一个包含 `1875` 条推广的真实店铺窗口完成回归：

| 项目 | 结果 |
|---|---:|
| 单页 10 条 | 成功 |
| 单页 20 条 | 成功 |
| 单页 50 条 | 成功 |
| 单页 100 条 | 平台返回参数错误 `2000000` |
| 修复前上限 | 50 页，只能读取 1000 条 |
| 修复后读取 | 1875/1875 条 |
| 分页数 | 38 页 |
| 并发数 | 4 |
| 完整读取耗时 | 约 8.1–9.6 秒 |
| 最终错误 | 无 |

同时将 SPU 列表改为按需渲染和搜索，一次最多显示 100 个匹配结果，避免大店铺一次创建 1875 个卡片造成界面卡顿。

另一个 `496` 条推广的店铺对每页 50 条返回 `5000000`，对每页 20 条正常，但部分分页会间歇性返回 `5000000`。最终稳定方案为每页 20 条、串行读取和每页最多 5 次退避重试，完整读取 `496/496` 条，耗时约 35 秒，最终无错误。

## 8. 验收建议

先发布只读版，再用单一指定 SPU 做真实暂停 UAT。只有以下条件全部通过后，才允许开启 store-wide 自动暂停：

1. 完整分页读取。
2. 阈值边界正确。
3. 同一 SPU 只暂停一次。
4. 暂停后状态核验为 7。
5. 超时不重复提交。
6. 审计记录完整。
