## 0. 已确认决策（2026-10-16）

| # | 决策 | 对技术实现的影响 |
|---|---|---|
| 1 | 所有图片统一裁 1350×1800 | 裁剪窗两个输入框固定写 `1350 / 1800`（**主图必须显式改写**，默认是源图尺寸） |
| 2 | 背面图只上传一次 | 首轮上传并把**实际素材名登记**；后续轮次走「按名称搜索 → 选中」，不再上传（见 §5.3、§4.5 方案 A） |
| 3 | 接受放大 | 分辨率低于 1340×1785 只写警告日志，不阻断 |
| 4 | 自动提交 | 默认 `submitMode='auto'`；提交前执行本地自检（图片数/色值名/货号/无残留弹窗），不过则跳过该商品并报告 |
| 5 | 序号自适应 | 通过 `browser/list` 按 id 匹配窗口，界面展示接口返回的 `seq` |

历史细节见 [修改建议清单.md](./修改建议清单.md)。

## 1. 总体架构

```
┌──────────────────────────────────────────────────────────────┐
│  比特浏览器 窗口 Y2-18 (id: 9e6f73cc...)                      │
│                                                              │
│  ┌────────────────────────┐   postMessage   ┌──────────────┐ │
│  │ 扩展 UI（侧边栏/弹窗） │ <-------------> │ MAIN world   │ │
│  │ - 参数、文件夹导入     │                 │ 注入脚本     │ │
│  │ - 任务队列、进度、日志 │   chrome.runtime│ (真正干活)   │ │
│  └────────────────────────┘                 └──────┬───────┘ │
│             ▲                                      │ DOM 操作 │
│             │ chrome.storage                       ▼          │
│        ┌────────────┐                    ┌──────────────────┐ │
│        │ Service    │                    │ agentseller.temu │ │
│        │ Worker     │                    │ .com 页面        │ │
│        └────────────┘                    └──────────────────┘ │
└──────────────────────────────────────────────────────────────┘
```

### 1.1 为什么要「MAIN world 注入脚本」
1. 上传图片需要给页面的 `input[type=file]` 赋值。做法是构造 `DataTransfer` 再把 `File` 写进 `input.files`。
   - 该操作在 content script（隔离世界）里对页面 Input 赋值容易被组件库的自定义校验忽略，在页面上下文（MAIN world）里执行最贴近真实用户操作。
2. 选择文件夹需要调用 `window.showDirectoryPicker()`（File System Access API），该 API 必须在页面上下文中、且由**用户手势**触发。
3. UI（参数、进度、日志）放扩展侧边栏，避免和 TEMU 页面样式互相污染；两者用 `window.postMessage` + `chrome.runtime` 通信。

### 1.2 组件清单

| 组件 | 文件 | 职责 |
|---|---|---|
| Manifest | `manifest.json` | MV3，最小权限 |
| Service Worker | `background.js` | 任务队列持久化、标签页管理、跨标签页调度 |
| 页面注入脚本 | `page/main.js`（`world: MAIN`, `document_start`） | 所有 DOM 交互与上传 |
| Content Bridge | `content/bridge.js`（隔离世界） | 转发 postMessage ↔ chrome.runtime，隔离世界的兜底 |
| 侧边栏 UI | `panel/panel.html/js/css` | 参数、Excel、文件夹、进度、日志、报表 |
| Excel 解析 | `lib/xlsx-lite.js` | 纯前端解析 .xlsx（见 §6.2） |
| 工具库 | `lib/dom.js` `lib/wait.js` `lib/log.js` | 元素定位、等待、重试、日志 |

## 2. 运行环境与接入方式

### 2.1 比特浏览器本地 API（实测可用）

| 接口 | 方法 | 说明 |
|---|---|---|
| `http://127.0.0.1:54345/browser/list` | POST `{page,pageSize}` | 窗口列表（含 id / seq / name / status） |
| `http://127.0.0.1:54345/browser/open` | POST `{id}` | 打开/复用窗口，返回 `ws`、`http`(调试端口)、`driver`、`pid` |
| `http://127.0.0.1:54345/browser/close` | POST `{id}` | 关闭窗口 |

实测返回示例：
```json
{"success":true,"data":{
  "ws":"ws://127.0.0.1:65306/devtools/browser/611ae4fc-...",
  "http":"127.0.0.1:65306",
  "driver":"<BitBrowser缓存目录>\\chromedriver\\148\\chromedriver.exe",
  "seq":7512,"name":"Y2-18","pid":35476}}
```

> 注意事项
> - 本机系统代理为 `127.0.0.1:7897`，PowerShell `Invoke-RestMethod` 会走代理导致请求失败；调用本地 API 必须绕过代理（Python `http.client` 直连正常）。
> - 该 id 对应序号是 **7512**（需求文字写 7515），插件以 id 匹配、界面展示实际序号。

### 2.2 自动化通道（走查阶段使用，供插件调试参考）
插件本身在浏览器内运行，不需要外部驱动。但为了调试/回归，可复用走查时搭好的通道：

1. `POST /browser/open` 拿到调试端口（示例 `65306`）。
2. 启动与内核同版本的 chromedriver：`chromedriver.exe --port=9515`。
3. 建立会话附着到该端口：
   ```json
   POST http://127.0.0.1:9515/session
   {"capabilities":{"alwaysMatch":{"goog:chromeOptions":{"debuggerAddress":"127.0.0.1:65306"}}}}
   ```

配套工具已落在仓库里：`tools/bb.py`（无第三方依赖的 BitBrowser + WebDriver 客户端：JS 执行、原生点击、坐标点击、文件上传、截图、标签页管理），`probes/` 下是按步骤拆分的走查脚本。

### 2.3 插件安装方式
- 源码目录直接「加载已解压的扩展程序」到比特浏览器窗口（比特浏览器基于 Chromium，支持 MV3）。
- 需要通过比特浏览器的「扩展管理」把扩展绑定到目标窗口（或把扩展装到窗口所在环境）。

## 4. 关键流程实现要点

### 4.0 通用执行器
```js
// 所有点击统一走这里：真实鼠标事件 + 视口校验 + 重试
async function realClick(el) {
  el.scrollIntoView({ block: 'center', behavior: 'instant' });
  await sleep(300);
  const r = el.getBoundingClientRect();
  assert(r.top > 0 && r.bottom < innerHeight, '元素不在视口内');
  el.dispatchEvent(new MouseEvent('mousedown', { bubbles: true, clientX: cx, clientY: cy }));
  el.dispatchEvent(new MouseEvent('mouseup',   { bubbles: true, clientX: cx, clientY: cy }));
  el.dispatchEvent(new MouseEvent('click',     { bubbles: true, clientX: cx, clientY: cy }));
}
```
> 走查结论：`el.click()` 对 beast-core 的多个组件（查询按钮、素材卡片、确认按钮）**无效**，必须派发真实事件序列。

### 4.1 查询 SKC
```
确保类型下拉 = SKC（已是则跳过）
   ↓ 若需切换：mousedown 打开下拉 → 选中文本为 SKC 的选项
设置输入框值（原生 setter + input/change 事件）
   ↓
真实点击「查询」 → 轮询直到「全部 1」且结果行含该 SKC（超时 20s）
```

### 4.2 进入编辑页
```
点击行内「编辑」 → 等弹窗（文本含「编辑商品信息」）
   → 点击卡片「编辑其它商品信息」 → 等新标签页
   → 切到新标签页 → 等待 page-ready 信号：
     轮询「色值」表头出现 && 规格表存在 && 无「正在获取商品数据」横幅
```
> 编辑页首次加载会出现黄色横幅「正在获取商品数据，请勿关闭此页面」，必须等它消失再操作，否则操作会被数据刷新覆盖。

### 4.3 新增色值
```
循环 i = 1..n：
  realClick(`div[class*=product-skc_specItem] > a`)     // + 添加
  等待规格表行数 = 原行数 + i
  设置 #productSkcList[newIndex].mainSpec[0] input = `Mixed Color${i+1}`
     （点击后若出现配色面板，按 Esc 关闭）
  设置 #productSkcList[newIndex].extCode input = A
  校验该行 upload-trigger 的 class 不含 disabled
```

### 4.4 上传正面图（每个新增色值 1 张）
```
打开素材中心（点击该行 upload-trigger）
  → 给弹窗内 input[type=file] 赋 File（DataTransfer）
  → 等裁剪弹窗 → [可选] 设 宽/高 → 确认裁剪 → 保存
  → 等弹窗回到素材中心，且列表出现「新素材」
  → 点击该素材缩略图（用上传前后列表 diff 定位，不依赖名称序号）
  → 校验右下角「已选 1 个」 → 点击「确认」
  → 校验该行轮播图 img 数量 = 期望值
```

### 4.5 上传背面图（每个新增色值 X 张，跨色值复用）
```
第一轮：本地上传 X 张 → 裁剪(1350×1800) → 保存 → 选中 X 张 → 确认
后续轮：
  方案 A（建议）：不再上传，直接在素材中心按名称筛出这 X 张 → 选中 → 确认
  方案 B：仍走本地上传 → 若出现「无需重复上传」弹窗 → 关闭 → 改为从库中选中
```

### 4.6 提交
```
（默认）暂停并高亮「提交」按钮，等待人工点击
（可选自动）realClick(提交) → 等成功提示 / 失败原因 → 记录日志
```
> **提交环节本次未验证**，需要人工配合验证一次（是否有二次确认、是否报错、成功后列表状态如何变化）。

## 5. 图片上传技术方案（重点）

### 5.1 文件夹导入（满足「导入主图文件夹 / 导入背面图文件夹」两个按钮）
在注入的浮层/侧边栏中放置两个按钮：

```js
// MAIN world，由用户点击触发（必须有用户手势）
const dirHandle = await window.showDirectoryPicker({ mode: 'read' });
const files = [];
for await (const entry of dirHandle.values()) {
  if (entry.kind === 'file' && /\.(jpe?g|png|webp)$/i.test(entry.name)) {
    files.push(await entry.getFile());   // File 对象
  }
}
files.sort(naturalCompareByName);        // DWRG03 < DWRG010
```

兜底方案（不支持 File System Access API 时）：注入 `<input type="file" webkitdirectory multiple>`。

> 注意
> - 排序必须自然数字序（Windows 默认字典序会把 `DWRG010` 排到 `DWRG03` 前）。
> - `File` 可结构化克隆，可在 MAIN world / 隔离世界 之间用 `postMessage` 传递；但不能通过 `chrome.runtime.sendMessage` 传，因此**文件对象留在页面侧**，扩展侧只传「第几张」的指令。
> - 目录句柄可存 `IndexedDB` 复用，但再次使用可能需重新授权，UI 上要给出「重新选择文件夹」入口。

### 5.2 给页面 input 赋值
```js
const dt = new DataTransfer();
dt.items.add(file);
input.files = dt.files;
input.dispatchEvent(new Event('input', { bubbles: true }));
input.dispatchEvent(new Event('change', { bubbles: true }));
```
实测：直接赋值后 TEMU 会正常进入上传流程并弹裁剪窗（走查时用 chromedriver 的 `DOM.setFileInputFiles` 等价验证通过）。

### 5.3 定位「刚上传的那张图」
素材名称会变成 `原文件名-序号`，序号不可预测，因此：
- 上传前记录列表快照（名称集合 / 首个卡片 id），上传后取差集；
- 或按「上传列表」浮层里的记录行（`素材名称 + 素材状态`）定位；
- 兜底：把素材按上传时间倒序，取第一项。

### 5.4 上传结果判定（需求里的「上传列表显示上传成功」）
优先级：
1. 「上传列表」浮层出现该素材且 `素材状态 = 上传成功`；
2. 素材中心网格出现该素材（名称/缩略图可见）；
3. 兜底：轮询 30s，超时按失败处理并截图。

> 实测：「上传列表」在无任务时显示「暂无上传记录」，因此不能只看这个浮层，需配合方案 2。

## 6. 数据与状态管理

### 6.1 任务模型
```ts
type SKC = string;

type TaskState = {
  skc: SKC;
  spu?: string;
  status: 'pending'|'running'|'blocked'|'done'|'failed'|'skipped';
  currentColorIndex: number;       // 已完成的色值数
  colorRows: Array<{
    index: number;                 // 在规格表中的行号
    name: string;                  // Mixed Color2 ...
    artNo: string;
    frontUploaded: boolean;
    backUploaded: boolean;
    backImageNames?: string[];     // 复用的背面图素材名
  }>;
  error?: { step: string; message: string; screenshot?: string };
  startedAt?: number; finishedAt?: number;
};

type TaskConfig = {
  skcList: SKC[];
  artNoPrefix: string;             // A
  n: number;                       // 1..7
  backCount: number;               // X
  submitMode: 'manual'|'auto';
  cropFrontTo1350x1800: boolean;
};
```

### 6.2 持久化
- `chrome.storage.local`：
  - `config`：任务配置
  - `tasks`：任务数组 + 进度（用于断点续跑）
  - `mainImageCursor`：主图取图游标（全局唯一、不复用）
  - `logs`：滚动日志（保留最近 2000 条）
- 断点续跑：启动时若存在未完成任务，提示「继续上次任务 / 重新开始」。

### 6.3 Excel 解析
`.xlsx` 本质是 zip。为避免外部依赖，采用：
1. `DecompressionStream('deflate-raw')`（Chrome 103+）解压 `xl/worksheets/sheet1.xml` 与 `xl/sharedStrings.xml`；
2. 用 `DOMParser` 解析，取 B 列（识别表头 `skc ID`，否则取第一列纯数字）；
3. 兜底：支持粘贴多行文本 / `.csv`。

走查确认的表结构：`A 列=序号`、`B 列=skc ID`，表头行可跳过。

## 7. 错误码与处理策略

| 错误码 | 场景 | 处理 |
|---|---|---|
| `E_LOGIN` | 跳转到登录页 | 暂停任务，提示登录后点「继续」 |
| `E_NO_RESULT` | SKC 查不到 | 跳过并记入报表 |

## 16. v0.3.0 / v0.4.0：首次真实自动提交暴露的问题与修复

用户第一次执行「处理完自动提交」时，跑到一半暂停。复盘日志与页面状态后定位到 3 个缺陷，并补齐 1 个缺失步骤。

### 16.1 缺陷：新色值行的「货号」没被填上（v0.3.0 修复）
- 现象：页面第 2 行 `Mixed Color2` 的货号为**空**。
- 原因链：
  1. `setColorName()` 写完后**立即**读回校验，而 React 提交是异步的 → 误判「色值写入失败」直接抛错；
  2. 抛错发生在 `setArtNo()` 之前 → 货号永远没写；
  3. 续跑逻辑里「该色值行已存在」时**整段跳过**（含货号），所以补不回来。
- 修复：
  - `setColorName` / `setArtNo` 改为**轮询确认**（最长 8 秒，两种写入方式各试一次），不再误判；
  - `stepEdit` 每轮循环都执行 `setColorName` + `setArtNo`，函数内部**幂等**（值已正确就直接返回）。

### 16.2 缺陷：失败重试会留下空色值行（v0.3.0 修复）
- 现象：页面多出一行「色值名空 / 无图」的空行。
- 原因：重试时又点了一次「+ 添加」。
- 修复：新增 `findReusableEmptyRow()`，**优先复用**已存在的空行；`addColorRow()` 增加重试与 45 秒等待。

### 16.3 缺陷：主图「不复用」的取图记录会被重置（v0.3.0 修复）
- 现象：点「停止」会把 `frontCursor` 归零，续跑时可能重复使用已用过的正面图。
- 修复：改为按**文件名记录已用主图**（`state.usedFrontImages`，持久化到 IndexedDB），`pickFrontFile()` 跳过已用文件；「停止」不再清空该记录。
- 迁移：首次升级时用素材库搜索 `DWRG` 得到的已用清单（`DWRG03`–`DWRG07`）初始化。

### 16.4 缺失步骤：敏感属性与体积重量（v0.4.0 新增）
- 现象：新增色值后，平台要求填写 `敏感属性与体积重量`（每个颜色 × 每个尺码一行：敏感属性、体积 长/次长/最短、重量）；不填无法提交。
- 实测结论：
  - 该表格的行**在色值名 + 货号填好后才会出现**（我们实测：填完货号，表格从 6 行变 12 行）；
  - 原色值（第一行颜色）的字段是 `disabled`，新增色值行可编辑；
  - 「敏感属性」是只读下拉（`是否敏感品：否/是` + 敏感属性多选），体积/重量是普通输入框。
- 实现：`fillSensitiveAndWeight()`
  1. `parseWeightRow()` 解析每行（颜色/尺码/敏感属性/体积/重量/是否可编辑），按「分组首行有 5 个单元格」区分分组；
  2. 以**第一个颜色**的各尺码取值为基准；
  3. 对每个可编辑行（即新增色值）：`pickSensitiveOption()` 选同样的敏感属性、`setInput()` 写体积与重量，按尺码一一对应；
  4. 在提交前调用，并把结果纳入 `preflightCheck()`（任一新增行的敏感属性/体积/重量为空则不提交）。

- v0.4.0：敏感属性与体积重量照抄。

### 16.6 v0.4.1：色值名写入失败的真正原因（真实输入通道）
- 现象：v0.4.0 里 `色值 → Mixed Color2` 依旧报「色值写入失败（期望 Mixed Color2，实际 ）」。
- 排查过程（逐个否定）：
  1. 原生 setter + `input` 事件 → 值被 React 回滚；
  2. `_valueTracker` 重置 → 无效；
  3. `beforeinput` / `paste` 事件 → 无效；
  4. `document.execCommand('insertText')` → 返回 true 但值仍为空；
  5. 用 WebDriver 真实按键 → **成功**。
- 结论：该色值下拉只接受**可信输入事件（isTrusted=true）**，页面内脚本无法伪造。
- 方案：新增 `debugger` 权限，页面脚本 → content bridge → Service Worker → `chrome.debugger.attach` + `Input.insertText`，插入完成立即 detach。
  - 对应代码：`page/main.js` 的 `typeTextViaDebugger()/typeTextReal()`、`setInput()` 的真实输入回退；`background.js` 的 `TYPE_TEXT` 分支；`content/bridge.js` 的转发。
  - 实测：`TYPE_TEXT` 返回 `{ok:true}`。

### 16.7 部署踩坑（重要，写给后续维护）
- **扩展重载必须"真实点击"**：用 JS `element.click()` 点 chrome://extensions 上的「重新加载」不会生效（Chrome 要求用户手势），
  我们一度以为升级成功，实际仍在跑旧代码（面板版本号一直显示旧值就是这个原因）。
- **重启比特浏览器窗口可以强制重载**，但会把 TEMU 登录态一起清掉（会话 cookie 未持久化），所以不推荐。
- 可靠做法（已实现为脚本 `tools/os_click_reload.py`）：
  1. 把 chrome://extensions 标签页 `Page.bringToFront`（否则页面不渲染，元素 rect 全为 0）；
  2. 计算「重新加载」按钮的屏幕坐标：`screenX + rect.x`、`screenY + (outerHeight - innerHeight) + rect.y`；
  3. 用 `SetForegroundWindow` + `SetCursorPos` + `mouse_event` 发送**系统级鼠标点击**；
  4. 校验扩展卡片版本号变化即成功。
- 升级流程（给同事）：解压新包 → 覆盖原目录 → 在 chrome://extensions 点一次「重新加载」。

## 19. v0.5.1 / v0.5.2：导入失效修复 + 首次真提交的结果

### 19.1 SKC 导入无反应（v0.5.1 修复）
- 现象：选择 Excel 后没有任何反应，列表一直「未导入」。
- 根因：面板初始化里 `shadow.getElementById('nextSku').onclick = onNextSku;` 引用了**不存在的函数** `onNextSku`，
  抛 `ReferenceError` 后 `buildPanel()` 中断——`impSkc/start` 之后的**所有按钮都没绑上**（包括 `skcFile.onchange`）。
- 修复：补上 `onNextSku()`（半自动模式下人工提交后进入下一条 SKC）。
- 验证：导入 `skc ID.xlsx` 成功解析出 2 个 SKC。
- 另外发现一个部署陷阱：用户后来是从**新解压的 `TEMU图片助手v0.5.0` 目录**加载扩展的，
  而脚本一直在更新旧目录 → 提示"已部署但版本不变"。现在改为**按 Secure Preferences 中的实际路径部署**。

### 19.2 首次真实提交的结果（重要）
- SKC `46350409750` 完整跑完：4 个新色值 + 正面图 + 背面图 + 敏感属性/体积/重量 → 点击提交。
- 但复查该商品的编辑页：**仍然只有 1 个色值**，说明**提交被平台拒绝**（我们只看到"提交结果未识别"）。

### 19.3 平台真正的拦截原因（v0.5.3 发现）
第二次真跑时，v0.5.2 的"3 轮补齐 + 抓 Toast"生效，平台明确提示：

```
请输入申报价格
请选择SKU分类
```

- **申报价格**：每个站点一个输入框，原色值行是 `100`，新颜色行是空的；
- **SKU分类**：只读下拉，原色值行是「单品」，新颜色行是「请选择SKU分类」。

1. 以第一个颜色值为基准，按尺码取每个站点的申报价格；

3. SKU分类通过下拉选择「单品」；
4. `preflightCheck()` 增加这两项校验（严格模式会拦住）。

## 21. v0.7.2–v0.7.3：修复「请选择skc颜色」、申报价格被改成300和表单未落盘

### 21.1 实跑现场与根因
平台对 `Mixed Color2` 的输入框显示了文字，但内部表单并未把它登记为有效 SKC 颜色。提交后：
- `productSkcList[1].mainSpec[0]` 出现「请选择skc颜色」；
- 同一行输入框的 `value` 已是 `Mixed Color2`，但 `placeholder` 仍是「选择或自定义颜色」；
- 手动点击输入框外触发失焦后，错误立即消失，`placeholder` 变为 `Mixed Color2`。

结论：色值组件必须在输入后触发真实的 `blur / focusout`，只写 DOM 或只发 `input/change` 不算完成。

同类问题也出现在价格、体积和重量输入框：界面显示数值，但 React 表单状态没有提交，平台校验仍报空。

### 21.2 修复内容
1. `setColorName()`：写入后执行 `commitInput()`，成功判据改为：
   - `input.value === Mixed ColorN`
   - `input.placeholder === Mixed ColorN`
   - 行内没有「请选择skc颜色」
2. 新增 `commitInput()` / `setInputCommitted()`，价格、货号、体积、重量、库存输入均在写入后失焦并等待状态落盘。
3. `fillSkuInfo()` 拆成四个阶段：
   - `fillSkuPricesFromBase()`：以混合色为基准，按「尺码 + 站点 form id」复制；
   - `fillSkuCategories()`：逐行选择 SKU 分类，并重新解析表格确认；
   - `fillSkuCodes()`：重新定位当前行后写 SKU 货号；
   - `fillSkuStocks()`：同一色值优先只开一次库存弹窗，确认整组是否被批量带上。
4. 申报价格不再统一写 300。混合色各站点实际价格是唯一基准，300 只作为某个站点基准为空时的备用值。
5. `preflightCheck()` 增加无效色值、逐站点价格不一致检查。
6. 提交后若平台仍有可见 `.Form_itemError`，直接读取原文并返回失败，不再只依赖一闪而过的 Toast。
7. 面板字段改名为「备用申报价（元）」，避免误以为会全站统一填 300。

### 21.5 v0.7.3：色值框必须走 trusted 键盘 + trusted 鼠标
v0.7.2 首次实跑仍失败，现场表现为：
- 输入框 `value=Mixed Color2`；
- `placeholder=选择或自定义颜色`；
- 页面内调用 `blur()` / 派发 `focusout` 后仍不变；
- 用 WebDriver 真实全选输入后再用系统鼠标点击页面左侧空白区，`placeholder` 立即变成 `Mixed Color2`。

## 24. v0.8.6：离开网站事故根因与超时跳过

### 24.1 事故现场
截图现场：
- 当前 SKC：`72790847079`
- 阶段：EDIT
- 素材中心搜索：`DWRG12`
- 素材中心仍打开
- 浏览器显示“离开此网站？系统可能不会保存您所做的更改。”

### 24.2 根因链
1. 新主图 `DWRG12.png` 为 8.72MB，1792×2400。
2. 平台轮播图要求单图小于 2MB。
3. 批量选择 4 张后，裁剪窗只出现 3 张；`DWRG12.png` 被平台静默丢弃。
4. 前 3 张写入后，代码继续搜索 `DWRG12`，等待后抛错“素材中心里找不到 DWRG12”。
5. 旧版 `onError` 在自动重试时直接执行 `location.href`。
6. 编辑页有未保存内容，浏览器触发 beforeunload “离开此网站”确认。
7. 自动化脚本不能操作浏览器原生确认框，任务因此永久卡住。

### 24.3 修复
1. `ensureUploadableImage()`：上传前检测文件大小；超过 1.9MB 时用 Canvas 等比转 JPEG，保持原像素尺寸并循环降低质量直到小于 2MB。
2. `safeNavigate()`：插件内部跳转统一通过 `chrome.debugger + Page.navigate`。
3. Background 监听 `Page.javascriptDialogOpening`；只对插件发起的导航自动点击“离开”，用户在正常页面上的确认框不受影响。
4. 普通导航失败时仍保留 `location.href` 兜底，并记录错误。

### 24.4 单 SKC 超时跳过
- 新增参数 `skuTimeoutMin`，默认 10 分钟，可配置 3–120 分钟。
- `state.current.startedAt` 记录当前 SKC 首次进入时间。
- 每 5 秒检查一次；超时后：
  1. 设置 `skcTimedOut`，所有 `assertRunning` / `waitFor` 立即中止；
  2. 回写状态“超时跳过（超过 N 分钟）”；
  3. 清理 retry 与 submitAttempt；
  4. cursor 前进到下一 SKC；
  5. 使用受控导航返回列表页；
  6. 最后一条 SKC 超时则结束任务并自动下载状态 Excel。
- 看门狗有 `timeoutNavigating` 防重复触发，避免并发跳过多个 SKC。

### 30.1 状态分类

| 最终状态前缀 | 分类 | 可重试 |
|---|---|---|
| `提交成功` | 成功 | 否 |
| `失败`、`待确认` | 失败 | 是，准备类错误除外 |
| `超时跳过` | 超时跳过 | 是 |
| 其他状态或没有状态 | 待处理 | 否 |

任务最终状态：
- `success`：该任务全部 SKC 成功；
- `partial`：至少一个成功，同时仍有失败或超时；
- `failed`：没有成功，且存在失败或超时；
- `paused`：运行中遇到需人工处理的问题，保留当前进度。

### 30.2 SKC 运行范围

任务状态新增 `runScopedSkcs`。普通运行使用完整 `skcs`；点击“重试失败（N）”时只把可重试 SKC 写入该数组，`cursor` 从 0 开始，因此成功项不会被再次访问。任务跨页或刷新后范围仍保留。

每个 SKC 的状态记录扩展为：

```json
{
  "status": "失败：xxx",
  "at": 1790000000000,
  "attempts": 2,
  "lastReason": "失败：xxx",
  "retryable": true
}
```

进入列表查询时尝试次数加 1；超过 3 次仅写警告日志。

### 30.3 重试队列

“重试失败（N）”执行以下步骤：

1. 汇总全部任务中的失败、待确认和超时 SKC；
2. 为涉及任务建立独立 `runScopedSkcs`；
3. 把这些任务标记为 `retryOnly=true`，并按任务列表顺序执行；
4. 重试队列只继续 `retryOnly` 任务，不会混入普通准备任务；
5. 队列结束后清除临时范围和标记，最终统计仍保留在 SKC 状态中。

准备类错误（主图不足、目录缺失、清单为空等）设置 `retryable=false`，任务卡仍可重新“保存准备”，但不会进入自动重试。

### 30.4 主图回滚

每个 SKC 开始查询时记录 `usedFrontStart`。超时跳过或最终失败时：

```text
frontCursor = frontCursorStart
usedFrontImages = usedFrontStart
```

自动重做 1 次、超时跳过、最终失败和提交确认未闭环均走同一回滚路径。成功提交不回滚。

### 30.5 Excel 运行汇总

回写时保留原有状态列，并创建或更新 `运行汇总` 工作表。该工作表包含：
- 当前任务与队列的 SKC 汇总；
- SKC、最终状态、分类、尝试次数、最近原因、更新时间；
- 插件版本、货号、源文件名和导出时间。

写入使用内联字符串，不依赖原工作簿的共享字符串表；已有同名工作表时原位替换，避免重复添加。

### 30.6 队列完成规则

任务结束时不再无条件记为 `done`，而是按该任务全部 SKC 状态计算 `success / partial / failed`。自动队列只继续准备完成、暂停待继续或本轮重试任务；队列结束后统一输出成功、失败、超时和待处理总数。

## 35. v0.9.9：卡死监测与面板自由拖动

### 35.1 从总耗时改为无进展时间

旧逻辑：

```text
elapsed = now - current.startedAt
elapsed >= limit → 超时跳过
```

新逻辑：

```text
elapsed = now - current.lastProgressAt
elapsed >= limit → 卡死超时
```

`lastProgressAt` 在每个有效步骤后更新：

- SKC/SPU 查询和命中；
- 每个色值名称与货号写入；
- 每个素材查找、选择、确认；

- 价格风险、二次确认、商品信息确认等平台弹窗处理。

仅在长时间没有上述有效进展时跳过，因此单个商品即使总处理时间超过阈值，只要仍在正常前进就不会被误判。

### 35.2 状态与重试

超时状态前缀改为 `卡死超时`，同时兼容旧版 `超时跳过`。两种状态都按超时分类并进入失败重试范围。

### 35.3 自由拖动

- 标题栏内除按钮外任意位置可拖；

- `button / input / select / textarea / a / label / 日志 / 设置 / 任务卡` 不触发拖动；
- 触摸屏只允许从标题栏拖动，避免与滚动冲突；

```text
Mixed Color4：0 张
```

但同一商品的其他色值仍有图片，说明并非真实全部缺失，而是 DOM 临时未挂载。

### 41.2 持久确认记录

`state.current.confirmedImages[colorName]` 保存本轮完成后确认写入的图片数量：

```text
confirmedImages["Mixed Color2"] = 3
```

每次色值图片确认并达到预期数量后立即写入；后续步骤和页面刷新都随 `state.current` 持久化。

### 41.3 自检取值

```text
verifiedImages = max(DOM 当前 img 数, confirmedImages 记录)
```

只有两边都少于 3 张才报错。DOM 为 0、确认记录为 3 时通过并记录原因。

### 41.4 重新挂载检查

新增 `revealCarouselRow(rowIdx, expected)`：

1. 将色值行轮播图单元滚入视口；
2. 等待 350ms；
3. 最多等待 3 秒让平台重新挂载图片；
4. 重新读取实际数量。

重试或续跑 `stepEdit()` 使用该函数，避免把已有图片误认为缺图而重复上传。

## 45. v0.10.9：自定义边缘伸缩手柄

### 45.1 问题

原生 `resize: both` 在部分比特浏览器内核中不响应，或拖动右下角时被整体拖动逻辑抢占，表现为“拉不动、面板被拖着走”。

### 45.2 方案

- 关闭原生 `resize`（`resize: none`）。
- 在 `.box` 内增加三个透明伸缩区，`z-index: 22`：
  - `.resizer.ew`：右边缘，宽 10px，整高，`cursor: ew-resize`，左右拉伸；
  - `.resizer.ns`：下边缘，整宽，高 10px，`cursor: ns-resize`，上下拉伸；
  - `.resizer.nwse`：右下角 18×18，`cursor: nwse-resize`，四角缩放。
- `pointerdown` 先识别 `.resizer`，命中则进入独立 `resizing` 状态并 `preventDefault()`，不再进入 `drag` 移动分支。
- `.resizer` 加入 `noDrag` 白名单，避免被空白区拖动逻辑捕获。

### 45.3 尺寸与保存

- 最小 360×320；最大宽 `min(760, window-40)`，最大高 `min(94vh, window-40)`。
- 右/下边缘只改对应维度，右下角同时改宽高；改动时同步更新 `host` 的 `left/top`、`box` 宽高、`uiState.panelSize` 和 `uiState.pos`。
- `pointerup` / `pointercancel` 时 `saveUI()` 持久化位置与尺寸，刷新页面后沿用。

## 46. v0.10.10：伸缩方向与底部空白修复

### 46.1 伸缩方向

v0.10.9 在拉伸时反向更新 `host.left = boxRight - width`、`host.top = boxBottom - height`，等于把右边缘/下边缘钉死，面板向反方向生长。

v0.10.10 改为左上角锚定：`pointerdown` 开始时把 `host` 的 `left/top` 固定为当前 `boxRect.left/top`，`right/bottom` 置 `auto`；`pointermove` 只更新 `box` 宽高，不再改写 `left/top`。

约束改为相对左上角：

```text
maxW = min(760, window.innerWidth - boxLeft - 8)
maxH = min(94vh, window.innerHeight - boxTop - 8)
```

### 46.2 底部空白

`.bd` 原先有 `max-height: 78vh` 和更早的 `max-height: 70vh` 两处上限，面板拉高后内容区不填满，底部留白。现改为：

```text
.bd.open { display: flex; flex-direction: column }
.bd { flex: 1; min-height: 0; overflow: hidden; max-height: none }
.pane { flex: 1; min-height: 0; overflow: auto; max-height: none }
.footer { 去掉 position: sticky，作为普通 flex 子项贴底 }
```

活动页签自动占满剩余高度并内部滚动，底部操作按钮始终可见。

## 49. v0.10.13：素材选中数量与弹窗隔离

### 49.1 事故现象

新增 `Mixed Color2–5` 和货号成功，素材卡片也能被定位；手动观察页面会出现已选数量，但插件最终报：

```text
第 2 行选中数量不符（期望 4，实际 0）
```

连续 6 次运行均在同一位置失败。

### 49.2 根因

`selectedCount()` 每次都会重新查找“最后一个可见素材中心”，而不是读取当前流程持有的弹窗。素材中心、去重提示和上传浮层并存时，可能读到另一个残留的 `已选 0 个`。

同时，旧流程只在四张图全部点击后统一比较数量，没有验证每次点击是否生效。

### 49.3 修复

- 增加 `activeMaterialDialog`，打开素材中心时绑定当前弹窗。
- 所有搜索、素材卡片查找、数量读取只使用当前绑定弹窗，失效后才重新解析。
- 点击卡片后最多等待 1.5 秒，确认已选数量增加。
- 点击未生效时依次尝试：选择框、名称上方缩略图、卡片上方、卡片中心。
- 每个素材选择后检查累计数量，发现数量回退或未按 1、2、3、4 递增时立即记录具体素材与前后数量。
- 关闭确认后的素材中心时清空绑定。

### 49.4 回归测试

新增 `tools/test_v01013_material_selection.py`：

- 构造当前 `已选 4 个` 弹窗和 DOM 后面残留的 `已选 0 个` 旧弹窗，验证读取当前弹窗。
- 构造可点击卡片，验证选中后数量从 0 增加到 1。
